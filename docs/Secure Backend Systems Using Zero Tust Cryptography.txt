Secure Backend Systems Using Zero Tust Cryptography

Rezumat
Aceasta lucrare prezinta proiectarea unui backend securizat, conceput pentru un sistem distribuit in care confidentialitatea, integritatea si verificabilitatea nu sunt efecte secundare ale implementarii, ci obiective arhitecturale explicite. Nucleul platformei este realizat in TypeScript, prin NestJS, insa modelul de securitate nu se sprijina pe un singur runtime, pe un singur serviciu si nici pe un singur depozit de incredere. Dimpotriva, proiectul fragmenteaza deliberat responsabilitatile intre componente specializate scrise in TypeScript, Rust, Rust-WASM, Go, Kotlin, Java si Python. Aceasta compartimentare reduce suprafata de compromitere si impiedica acumularea starii criptografice complete intr-o singura entitate executabila. Datele sensibile sunt protejate prin AES-256-GCM si derivare HKDF, parolele sunt securizate prin Argon2id, identitatile interne sunt semnate Ed25519, iar evenimentele de securitate sunt inlantuite prin hash-uri SHA3-256. In paralel, PostgreSQL este utilizat nu doar ca infrastructura tranzactionala, ci si ca mecanism nativ de imutabilitate, control al mutatiilor si verificare a lanturilor de integritate. Arhitectura Zero Knowledge minimizeaza persistenta secretelor, iar abordarea Zero Trust elimina increderea implicita dintre servicii. Rezultatul este un backend verificabil, rezilient si adecvat unei discutii stiintifice asupra securitatii sistemelor distribuite moderne.

Cuvinte cheie: criptografie, Zero Trust, Zero Knowledge, MPC, backend securizat

1. Introducere
Problema centrala abordata in aceasta lucrare este urmatoarea: cum poate fi proiectat un backend modern astfel incat compromiterea partiala a unei componente sa nu antreneze compromiterea sistemica a intregii platforme? Intrebarea este relevanta deoarece numeroase backend-uri contemporane concentreaza in acelasi proces autentificarea, autorizarea, persistenta, semnarea token-urilor, criptarea datelor si observabilitatea. O asemenea concentrare este eficienta pe termen scurt, dar fragila din punct de vedere al securitatii. Daca procesul central este compromis, aproape toate garantiile de securitate devin iluzorii.

Proiectul analizat propune o directie diferita. In locul unei entitati unice de incredere, sistemul introduce un ansamblu de servicii specializate, fiecare delimitat prin contracte, politici, identitati proprii si canale securizate. Astfel, securitatea nu mai depinde de absenta erorilor intr-un singur server, ci de convergenta mai multor mecanisme independente: criptografie autentificata, service assertions, mTLS, politici OPA, jurnalizare hash-chained, trigger-e de imutabilitate in baza de date si controale runtime la nivel de container.

2. Contextul proiectului si delimitarea domeniului
Filspresso Next nu este un simplu backend monolitic, ci un ecosistem de componente distribuite, fiecare avand o responsabilitate distincta. In forma actuala a repository-ului, arhitectura operationala cuprinde:

- `nestjs-backend/`, runtime-ul backend principal, bazat pe TypeScript si NestJS
- `rust-crypto-service/`, serviciul criptografic separat pentru commitment si verify
- `rust-wasm/`, modulul browser-side pentru preprocessare determinista si commitment local
- `go-ops-service/`, serviciul operational pentru ingestie de evenimente, mTLS si identitate SPIFFE
- `java-invoice-service/`, serviciul de randare si securizare a documentelor invoice
- `kotlin-subscription-service/`, serviciul dedicat fluxurilor de subscription
- `app.py`, `models/` si rutele Python, pentru componente auxiliare si AI
- `security/`, pentru politicile de runtime si admission control
- `infrastructure/`, pentru componenta de transparency backend si control IaC

Prin urmare, backend-ul nu trebuie inteles ca un singur proces HTTP, ci ca o federatie de componente, in care planul de business, planul criptografic, planul de observabilitate si planul de transport securizat sunt separate in mod intentionat.

3. Ipoteza arhitecturala a lucrarii
Lucrarea se sprijina pe trei ipoteze de proiectare:

1. O arhitectura securizata nu trebuie sa concentreze autoritatea totala a sistemului intr-o singura instanta executabila.
2. Datele sensibile trebuie stocate, procesate si retransmise numai in forme minim necesare si criptografic verificabile.
3. Integritatea operationala trebuie ancorata sub nivelul aplicatiei, prin mecanisme native de storage si de control al mutatiilor.

Aceste ipoteze structureaza toate alegerile tehnologice si toate deciziile de design.

4. De ce a fost aleasa o arhitectura multi-limbaj si multi-serviciu
Un observator superficial ar putea considera utilizarea simultana a TypeScript, Rust, Rust-WASM, Go, Kotlin, Java si Python drept un exces de complexitate. In realitate, tocmai aceasta eterogenitate controlata este unul dintre argumentele forte ale proiectului.

In primul rand, limbajele sunt alese in functie de profilul problemei:
- NestJS este adecvat pentru orchestrare, middleware, guards, validare si compozitie modulara.
- Rust este adecvat pentru cod criptografic determinist, cu suprafata mica de dependinte si predictibilitate ridicata.
- Rust-WASM este adecvat pentru reproducerea exacta, in browser, a unor primitive deterministe folosite si in backend.
- Go este adecvat pentru servicii de transport securizat, mTLS si ingestie operationala cu latenta redusa.
- Java si Kotlin sunt utile pentru servicii separate, contractuale, unde izolarea functionala este mai valoroasa decat uniformizarea stack-ului.
- Python ramane rezervat componentelor AI si auxiliare, fara a polua planul criptografic central.

In al doilea rand, aceasta fragmentare reduce riscul de compromitere sistemica. O vulnerabilitate intr-un modul Python nu implica automat compromiterea cheilor de service assertion. O eroare in serviciul de invoice nu implica automat alterarea logului de securitate. Un bug in frontend nu echivaleaza cu controlul asupra mecanismelor de commitment din Rust.

In al treilea rand, arhitectura devine mai explicabila. Fiecare strat are o functie distincta, un model de risc distinct si un set distinct de controale. Aceasta claritate este extrem de valoroasa intr-o lucrare academica, deoarece permite argumentare coerenta, fara confuzii intre planuri functionale.

5. Ideea centrala: The Server Cannot Be Hacked as a Single Entity
Una dintre ideile definitorii ale arhitecturii este ca backend-ul nu trebuie sa poata fi compromis ca entitate unica. Desigur, formularea nu inseamna imposibilitate absoluta in sens matematic, ci refuzul deliberat al unui model in care o singura instanta executabila detine:
- toate cheile
- toate secretele
- toate politicile
- toate traseele de verificare
- toate jurnalele
- intreaga autoritate de executie

In proiect, aceasta idee este operationalizata prin compartimentare:
- `nestjs-backend` coordoneaza, valideaza si orchestreaza, dar nu monopolizeaza planul criptografic.
- `rust-crypto-service` proceseaza commitment-uri si verificari deterministe, independent de logica comerciala.
- `go-ops-service` valideaza identitatea de transport si ingestia operationala sub mTLS si SPIFFE.
- `java-invoice-service` si `kotlin-subscription-service` mentin fluxuri distincte, contractuale, cu controale proprii.
- `rust-wasm` transfera o parte din preprocessarea determinista la nivel client, fara a expune secrete.

Aceasta fragmentare este apropiata conceptual de principiile MPC si de modelele de distributed trust. Chiar daca implementarea actuala nu este un protocol MPC complet pentru toate fluxurile, ea respecta intutia fundamentala a MPC: niciun nod singular nu trebuie sa concentreze intreaga stare sensibila si nici intreaga autoritate decizionala.

6. A doua idee centrala: The Storage Cannot Be Tampered With
A doua teza structurala a sistemului este ca integritatea storage-ului critic nu trebuie sa depinda exclusiv de corectitudinea stratului aplicativ. Daca jurnalul de securitate poate fi rescris liber de aplicatie, atunci auditul este slab prin definitie. In acest proiect, PostgreSQL este utilizat nu doar pentru persistenta, ci ca mecanism de control nativ al imutabilitatii si integritatii.

In `nestjs-backend/src/database/ensureAppSchema.ts` sunt definite:
- tabela `security_event_ledger`
- tabela `security_event_ledger_archive`
- constrangeri `CHECK` pentru validarea formatului hash-urilor
- trigger-ele `forbid_security_event_ledger_update` si `forbid_security_event_archive_update`
- rolurile `filspresso_security_writer` si `filspresso_security_reader`

In `nestjs-backend/src/common/utils/securityLedger.ts`, fiecare eveniment este serializat canonical, legat de hash-ul anterior si re-hash-uit cu SHA3-256. Astfel, integritatea istoricului nu mai este un atribut de buna credinta, ci o proprietate verificabila.

Aceasta distinctie trebuie exprimata riguros. Sistemul nu pretinde protectie la nivel de block device sau firmware. In schimb, el implementeaza ceea ce poate fi numit academic "database-native tamper evidence": imutabilitate si verificare ancorate in schema, trigger-e, roluri si lanturi hash, sub nivelul fluxului aplicativ obisnuit.

8. Zero Trust ca principiu de baza
Zero Trust inseamna, in contextul acestei lucrari, ca nicio cerere nu este tratata ca fiind legitima prin simpla apartenenta la reteaua interna. Fiecare apel trebuie justificat prin identitate, scop, context si non-repetabilitate. In proiect, acest lucru apare in cel putin patru straturi.

8.1. Identitatea utilizatorului
In `nestjs-backend/src/common/utils/auth-tokens.ts`, token-urile utilizatorilor sunt semnate EdDSA acolo unde exista cheie dedicata. Exista `issuer`, `audience`, `kid`, JWKS si suport pentru rotatia cheilor. Acest lucru muta modelul dinspre un simplu shared secret spre un model asimetric, mai coerent si mai auditabil.

[PLACEHOLDER COD 6 - "Semnarea JWT si expunerea JWKS"; sursa: `nestjs-backend/src/common/utils/auth-tokens.ts`; linii recomandate: 109-221]

8.2. Identitatea inter-servicii
In `nestjs-backend/src/common/utils/serviceAssertions.ts`, fiecare serviciu intern poate primi un token semnat Ed25519, continand `iss`, `sub`, `aud`, `scope`, `iat`, `nbf`, `exp`, `jti` si optional `op_id`. Verificarea acestor campuri impiedica:
- impersonarea unui serviciu
- folosirea unei identitati valide in afara scopului permis
- reutilizarea unei afirmatii expirate sau replay-ate

[PLACEHOLDER COD 7 - "Issue si verify pentru service assertions"; sursa: `nestjs-backend/src/common/utils/serviceAssertions.ts`; linii recomandate: 58-160]

In `nestjs-backend/src/common/utils/replayGuard.ts`, operatiile sunt legate de `operation_id`, `scope` si `actor_id`. Astfel, identitatea nu este suficienta; trebuie dovedita si unicitatea semantica a cererii. Aceasta este o distinctie extrem de importanta in sistemele financiare, administrative sau criptografice.

9. Criptografia de confidentialitate
Protectia datelor sensibile este implementata in `nestjs-backend/src/common/utils/encryption.ts`. Alegerea AES-256-GCM este justificata prin faptul ca ofera simultan:
- confidentialitate
- integritate
- detectie de tampering

Mai important, cheia efectiva nu este folosita brut, ci derivata prin HKDF, folosind context, versiune si `keyId`. Acest lucru inseamna ca acelasi material brut de intrare nu este reciclat necontrolat in contexte diferite. In plus, AAD leaga criptograma de contextul in care a fost produsa, ceea ce reduce riscul de re-utilizare necorespunzatoare.

Implementarea mai ofera:
- versionare a formatului criptat
- key rotation
- suport pentru chei legacy
- decriptare controlata pe keyring

Din punct de vedere academic, aceasta sectiune trebuie argumentata nu ca o simpla "criptare a datelor", ci ca un model de confidentialitate operationala in care datele sunt legate de context, cheile sunt derivabile si tranzitia intre generatii de chei este gestionabila.

[PLACEHOLDER COD 10 - "Derivarea cheii AEAD, AAD si fluxul encrypt/decrypt"; sursa: `nestjs-backend/src/common/utils/encryption.ts`; linii recomandate: 56-150]

10. Criptografia de autentificare si rezistenta la brute-force
In `nestjs-backend/src/common/utils/passwords.ts`, parolele sunt securizate prin Argon2id, nu prin hashing rapid. Aceasta alegere este esentiala. O parola nu trebuie doar "transformata", ci trebuie costisitor de verificat pentru un atacator. Parametrii `memoryCost`, `timeCost`, `parallelism` si `hashLength` definesc costul de calcul, iar suportul rezidual pentru bcrypt permite migrarea utilizatorilor existenti fara fractura de compatibilitate.

Academic vorbind, aceasta este o decizie de proiectare defensiva: securitatea nu se obtine numai prin alegerea unui algoritm modern, ci si prin strategiile de migrare si rehash controlat.

[PLACEHOLDER COD 11 - "Politica Argon2id si mecanismul de rehash"; sursa: `nestjs-backend/src/common/utils/passwords.ts`; linii recomandate: 13-69]

11. Rust crypto service: control-plane criptografic separat
`rust-crypto-service` reprezinta poate cea mai clara materializare a ideii ca planul criptografic nu trebuie diluat in logica de business. In `rust-crypto-service/src/main.rs`, serviciul:
- canonicalizeaza JSON
- calculeaza commitment-uri SHA3-256 cu separare de domeniu
- verifica inbound service assertions
- valideaza concordanta `operation_id`
- protejeaza fluxul impotriva replay-ului prin `jti`

Decizia de a izola acest plan in Rust are o motivatie dubla. Pe de o parte, Rust ofera predictibilitate si control strict asupra fluxurilor sensibile. Pe de alta parte, separarea operationala face ca backend-ul principal sa nu fie si executor, si arbitru, si depozit al intregii logici de verificare.

13. Zero Knowledge ca arhitectura de minimizare a cunoasterii
Componenta Zero Knowledge este orchestrata in `nestjs-backend/src/crypto/crypto.service.ts` si `nestjs-backend/src/crypto/crypto.controller.ts`. Ea nu trebuie descrisa reductiv, ca si cum ar fi doar o colectie de endpoint-uri crypto. In realitate, sistemul modeleaza:
- registru de circuite (`zk_circuit_registry`)
- guvernanta ciclului de viata al circuitelor
- sesiuni de proof (`zk_proof_sessions`)
- hash-uri pentru verification key, witness si context de proof
- verificare si jurnalizare a sesiunilor

Aspectul academic important este ca witness-ul nu este pastrat in clar, ci redus la amprenta sa criptografica. Cu alte cuvinte, backend-ul se straduieste sa retina ceea ce este verificabil, nu ceea ce este secret. Aceasta este una dintre expresiile cele mai clare ale unui design compatibil cu idealul Zero Knowledge.

15. Go Ops Service, mTLS si identitatea SPIFFE
`go-ops-service` ilustreaza foarte bine ideea ca identitatea logica a unui serviciu si identitatea sa de transport nu sunt echivalente, ci complementare. In `go-ops-service/main.go` sunt implementate:
- construirea configuratiei TLS
- activarea mTLS
- validarea certificatului client
- extragerea identitatii SPIFFE din URI
- allowlist pentru SPIFFE IDs
- verificarea service assertion Ed25519
- control operational prin API key

Ordinea acestor controale este remarcabila: mai intai transportul, apoi identitatea de serviciu, apoi scopul, apoi accesul operational. Aceasta este Zero Trust in forma sa inginereasca reala: increderea se construieste incremental, nu se presupune.

17. Java, Kotlin si Python: de ce merita mentionate
Arhitectura nu este valoroasa doar prin componentele sale criptografice, ci si prin delimitarea stricta a serviciilor adiacente.

In `java-invoice-service`, documentele PDF sunt generate si securizate separat de backend-ul principal. In `kotlin-subscription-service`, contractele pentru subscriptions sunt mentinute in flux propriu. In componentele Python, procesarea AI si functionalitatile auxiliare raman in afara planului de chei si de verificare criptografica centrala.

Aceasta separare este importanta intr-o lucrare academica pentru ca arata ca securitatea nu rezulta doar din "algoritmi buni", ci si din topologia sistemului si din disciplinarea frontierelor de responsabilitate.

20. Este utila o captura de ecran cu rezultatul testului?
Da, este o idee buna, cu o conditie importanta: captura de ecran trebuie folosita ca figura de sustinere, nu ca substitut al interpretarii. Intr-o lucrare academica, o imagine este convingatoare atunci cand:
- este clar etichetata
- este insotita de o analiza textuala
- nu ascunde limitele rezultatului

In acest caz, o captura a raportului strict este foarte potrivita, deoarece arata intr-o singura imagine:
- scorul general
- distributia pe categorii
- evidenta SLA
- punctul vulnerabil punctual

Recomandarea mea este sa incluzi o singura figura principala, nu mai multe capturi fragmentate. Figura trebuie sa fie insotita de un paragraf in care explici ca securitatea si fiabilitatea ating `100%`, iar performanta este buna, dar nu perfecta, din cauza latentei endpoint-ului de health.

23. Limitele arhitecturii si directii de maturizare
O lucrare serioasa nu evita costurile designului propus. Arhitectura prezenta este mai robusta, dar si mai exigenta:
- necesita observabilitate superioara
- impune management mai riguros al secretelor
- creste complexitatea operationala
- necesita contracte si politici bine intretinute

Pe termen lung, pot fi adaugate:
- integrare KMS/HSM pentru KEK si chei de semnare
- threshold signatures reale pentru MPC
- prover/verifier Zero Knowledge complet
- transparency anchoring automatizat
- rotatie automata de certificate si politici semnate

24. Concluzie
Arhitectura analizata demonstreaza o directie coerenta si maturizata de proiectare a unui backend securizat modern. Alegerea NestJS pentru orchestrare, Rust pentru verificare determinista, Rust-WASM pentru congruenta client-server, Go pentru identitate de transport, PostgreSQL pentru tamper evidence nativ, OPA pentru autorizare declarativa si mecanismele de replay protection, mTLS si hash chaining nu constituie o colectie arbitrara de tehnologii, ci expresia unei gandiri arhitecturale unitare. Proiectul urmareste explicit doua principii majore: backend-ul nu trebuie sa poata fi compromis ca o entitate singulara, iar jurnalul critic nu trebuie sa poata fi alterat fara detectie nativa. Datele experimentale sustin puternic aceasta directie, confirmand excelenta infrastructurii de securitate si de fiabilitate, cu o singura abatere minora de latenta in afara nucleului criptografic. Din aceste motive, proiectul este adecvat unei lucrari academice solide asupra criptografiei, securitatii backend-ului, Zero Trust, Zero Knowledge si rezilientei sistemelor distribuite.
